# Contract client codegen

`packages/codegen/generate.ts` turns the compiled Soroban contracts in
`packages/contracts` into TypeScript bindings under
`packages/sdk/src/generated/contracts/`. The bindings give the SDK typed
encoders and decoders for every contract type, typed operation builders for
every contract function, and decoders for every contract event.

This guide is for contributors. It covers what the generator reads, what it
writes, how to regenerate after a contract change, and how to extend it.

The generator never touches the network and does not need the `stellar` CLI.
It reads each contract's spec straight out of its WASM file.

---

## 1. Input: the Soroban contract spec

### 1.1 Which contracts are included

`discoverContracts()` reads `packages/contracts/Cargo.toml` and walks every
workspace member, in sorted order. A member is included only when its
`Cargo.toml` lists `"cdylib"` under `crate-type`. Anything else is skipped.

For each included crate the generator derives two names:

| Cargo package       | Module file        | Namespace export |
| ------------------- | ------------------ | ---------------- |
| `linkora-contracts` | `linkora.ts`       | `linkora`        |
| `linkora-vesting`   | `vesting.ts`       | `vesting`        |
| `linkora-referral`  | `referral.ts`      | `referral`       |
| `token-factory`     | `token-factory.ts` | `tokenFactory`   |

The `linkora-` prefix is stripped, except that the main `linkora-contracts`
crate maps to the module name `linkora`. `token-factory` has no prefix, so it
keeps its name. Hyphens become underscores before the namespace is camel-cased.
A crate with `crate-type` set to `cdylib` but no `linkora-` prefix is still
included, so check the name in the generated barrel after you add a contract.

### 1.2 Where the WASM comes from

The generator expects one file per crate:

```text
packages/contracts/target/wasm32v1-none/release/<crate_name>.wasm
```

The crate name has its hyphens replaced with underscores, so
`linkora-vesting` is read from `linkora_vesting.wasm`. The directory can be
overridden with `--wasm-dir <dir>`.

The WASM must be built for `wasm32v1-none`. The `build` script in
`packages/contracts/package.json` runs:

```bash
cargo build --target wasm32v1-none --release --workspace
```

If the Rust build fails, that script prints `Rust/wasm32v1-none build skipped`
and exits successfully. The generator then fails with
`WASM for <crate> not found at ... — run 'pnpm build:contracts' first.` So a
missing toolchain shows up as a missing-WASM error, not as a build error.

### 1.3 What is read from the WASM

The generator calls `contract.Spec.fromWasm(...)` from `@stellar/stellar-sdk`.
That reads the `contractspecv0` custom section that `soroban-sdk` writes into
every contract. The section holds `xdr.ScSpecEntry` values, and each entry is
one of:

- **UDT entries**: `#[contracttype]` structs, unions, enums and `#[contracterror]`
  enums. Each one becomes a TypeScript type plus encode and decode functions.
- **Function entries**: contract methods. Names starting with `__` are skipped.
- **Event entries**: `#[contractevent]` definitions, with their topic prefix,
  topic and data parameters, and data format.

A `SPEC_HASH` is computed per module. It is the SHA-256 of the XDR of all spec
entries, so a bindings file records which spec it came from.

## 2. Output

Running the generator writes these files:

```text
packages/sdk/src/generated/
├── schema.hash              # "<sha256>  <crate>" per contract
└── contracts/
    ├── index.ts             # barrel: export * as <namespace> from "./<module>.js"
    ├── runtime.ts           # shared ScVal encoders/decoders (hand-written text, emitted)
    ├── linkora.ts           # one module per contract
    ├── referral.ts
    ├── token-factory.ts
    ├── multicall.ts
    └── vesting.ts
```

Every generated file starts with:

```ts
// Auto-generated by packages/codegen/generate.ts — do not edit manually.
// Regenerate with `pnpm codegen`; CI fails (`pnpm codegen:check`) when stale.
```

Do not edit these files by hand. Your change will be overwritten the next time
the generator runs, and CI will fail.

Each contract module (`<module>.ts`) contains the following sections.

### 2.1 Types

- **Structs** with named fields become an `export interface` plus
  `encode<Name>(v)` and `decode<Name>(v)`. The encoder writes a map keyed by
  field name, with keys sorted the way the host orders them.
- **Tuple structs** (fields named `0`, `1`, ...) become a TypeScript tuple type
  with the same encode and decode pair.
- **Unit-only unions** become a string-literal union, such as
  `export type Role = "Admin" | "Member";`, plus a `<NAME>_VALUES` constant.
- **Data-carrying unions** become a discriminated union on `tag`, such as
  `{ tag: "Transfer"; values: [bigint] }`.
- **Integer enums** (`#[contracttype]` enums with explicit values) become a
  TypeScript `enum` with `encode` and `decode` functions.
- **Contract error enums** become a `enum` plus a `<camelName>Name(code)`
  helper that returns the error name for a numeric code.

Scalar mapping, as used in the generated code:

| Soroban type                                                      | TypeScript type |
| ----------------------------------------------------------------- | --------------- |
| `bool`                                                            | `boolean`       |
| `u32`, `i32`, error codes                                         | `number`        |
| `u64`, `i64`, `u128`, `i128`, `u256`, `i256`, timepoint, duration | `bigint`        |
| `bytes`, `BytesN<N>`                                              | `Uint8Array`    |
| `string`, `Symbol`, `Address`, `MuxedAddress`                     | `string`        |
| `Option<T>`                                                       | `T \| null`     |
| `Vec<T>`                                                          | `Array<T>`      |
| `Map<K, V>`                                                       | `Map<K, V>`     |
| `Result<T, E>`                                                    | the `T` type    |
| `Val`                                                             | `xdr.ScVal`     |

Encoders validate their input. For example, `encodeU32` rejects a non-integer
or out-of-range value with a `RangeError`. Decoders validate the `ScVal` shape
and throw `DecodeError` (exported from `runtime.ts`) on anything unexpected.

### 2.2 Functions: arguments, results and client methods

For every contract function `foo_bar` the module emits:

| Emitted item                  | Purpose                                                  |
| ----------------------------- | -------------------------------------------------------- |
| `FooBarArgs` interface        | Typed arguments. Omitted when the function takes none.   |
| `encodeFooBarArgs(args)`      | Returns `xdr.ScVal[]` in call order.                     |
| `decodeFooBarResult(v)`       | Converts the returned `xdr.ScVal` into the result type.  |
| `methods.foo_bar`             | `{ name, encodeArgs, decodeResult }` entry in `methods`. |
| `<Name>Contract.fooBar(args)` | Returns an `xdr.Operation` for the contract call.        |

`methods` is an `as const` object. `MethodName` is `keyof typeof methods`.

The operation builder is a class named after the crate:

```ts
export class LinkoraContract {
  constructor(public readonly contractId: string) {}
  // one method per contract function, returning xdr.Operation
}
```

Each method builds an `invokeHostFunction` operation. The caller adds it to a
transaction, simulates, signs and submits it as usual. The generator does not
submit anything.

### 2.3 Events

For every `#[contractevent]` the module emits:

- an `export interface <EventName>` with one field per event parameter;
- `<EVENT_NAME>_TOPICS`, the leading topic symbols as a readonly tuple;
- `decode<EventName>(topics, data)`, which checks the leading topics and the
  topic count (`expectTopics`) and then decodes the fields.

Topic parameters are read from `topics`. Data parameters are read from `data`,
either as a map (named fields), a vector (positional), or the single value,
depending on the event's data format.

A module with events also exports:

- `ContractEvent`, a union tagged by event name: `{ name, event }`;
- `decodeEvent(topics, data)`, which matches the first topic against each
  event's prefix and returns `null` when nothing matches.

Use `decodeEvent` when you have raw events from RPC and want a typed result.
If the topics do not belong to this contract, it returns `null`.

## 3. Using the bindings

Inside the SDK, import a module directly. The SDK does this already, for example
in `packages/sdk/src/multicall.ts`:

```ts
import * as linkora from "./generated/contracts/linkora.js";
```

Or import the barrel `packages/sdk/src/generated/contracts/index.ts`, which
exposes one namespace per contract (`linkora`, `vesting`, and so on). The
barrel is side-effect free, so bundlers can drop contracts that an app does
not use.

Typical flow:

1. Build the operation with `new linkora.LinkoraContract(id).<method>(args)`.
2. Simulate and submit the transaction as usual.
3. Decode the return value with `linkora.decode<Fn>Result(scVal)`, or decode
   events with `linkora.decodeEvent(topics, data)`.

Catch `DecodeError` where you decode untrusted RPC data. The decoders throw it
on a shape mismatch, and the message names the expected type.

### 3.1 Legacy wrappers

Several files in `packages/sdk/src/generated/` are hand-maintained wrappers
from before this generator was used: `client.ts`, `events.ts`, `types.ts`,
`index.ts` (one level up from `contracts/`), and `contract-parity.ts`. Each
starts with a comment saying the generator no longer emits it. Don't add new
code to them. New code should import from `generated/contracts/`.

## 4. Regenerating after a contract change

### 4.1 The commands

From the repository root:

```bash
pnpm codegen         # build the contracts to WASM, then regenerate the bindings
pnpm codegen:check   # build, regenerate in memory, and fail if any file is stale
```

Under the hood:

- `pnpm codegen` runs `pnpm build:contracts && pnpm --filter @linkora/codegen generate`.
- `pnpm codegen:check` runs `pnpm build:contracts && pnpm --filter @linkora/codegen check`.
- `generate.ts --check` compares each output in memory with the file on disk.
  It fails if a file differs, is missing, or if there is an extra file in
  `generated/contracts/` that the generator would not produce.

The generator also deletes any extra file in `generated/contracts/` when it
writes, so hand-written files in that folder will be removed.

### 4.2 Workflow

1. Change the contract in `packages/contracts`.
2. Run `pnpm codegen`. If the build fails, fix the Rust first. A
   `not found` error means the WASM was not built.
3. Review the diff under `packages/sdk/src/generated/`. A change to a struct
   field, a union variant, or an event shape shows up there.
4. Update the SDK code and tests that depend on the changed types.
5. Run `pnpm codegen:check`, then `pnpm --filter <sdk package> test`. The
   generated-contracts test
   (`packages/sdk/src/__tests__/generated-contracts.test.ts`) compares the
   encoders with stellar-sdk's own spec encoder for the committed WASM.
6. Commit the regenerated files together with the contract change.

### 4.3 What CI checks

Two workflows run the generator:

- The `codegen` job in `.github/workflows/ci.yml` and the step in
  `.github/workflows/sdk-e2e.yml` run `pnpm codegen:check`. They fail if the
  committed bindings are stale.
- `.github/workflows/deploy-testnet.yml` runs `pnpm codegen` against the
  deployed contract. It regenerates the bindings and does not compare them.

If CI reports `Generated contract bindings are out of date`, run `pnpm codegen`
locally and commit the result.

## 5. Extending the codegen

Start by deciding which kind of extension you need.

### 5.1 Adding a new contract

1. Add a crate under `packages/contracts/contracts/<name>/` with
   `crate-type = ["cdylib", ...]` in its `Cargo.toml`.
2. Add it to the workspace `members` list in `packages/contracts/Cargo.toml`.
3. Run `pnpm codegen`. The new module is discovered automatically and the
   barrel gains a `export * as <namespace>` line.

Crates without `cdylib` are ignored, so library-only crates do not generate
bindings.

### 5.2 Supporting a new spec type

If the generator throws `Unsupported spec type <name>`, the contract uses a
type that no switch case handles. Add a case in each of these methods in
`ModuleGen`:

- `tsType`: the TypeScript type to emit;
- `enc`: the expression that turns a TypeScript value into an `xdr.ScVal`;
- `dec`: the expression that turns an `xdr.ScVal` back into the TypeScript value.

If the encoding needs a helper, add it to the `RUNTIME` string at the bottom of
`generate.ts`. Helpers there are emitted into `runtime.ts`, so remember to
escape backticks and `${` inside the template string, as the existing helpers
do.

### 5.3 Changing the emitted shape

Emitter methods (`emitStruct`, `emitUnion`, `emitIntEnum`, `emitFunctions`,
`emitEvents`) build the output as arrays of lines. After changing one, run
`pnpm codegen` and check the diff on at least one real contract. The generator
formats its output with Prettier using the repository config, so you don't need
to format by hand.

### 5.4 Testing an extension

- Run `pnpm --filter @linkora/codegen typecheck`. It runs `tsc --noEmit`.
- Run the SDK's `generated-contracts.test.ts`. Add a case there when you change
  how a type is encoded, since that test compares against stellar-sdk's
  encoder.
- Run `pnpm codegen:check` to confirm the committed output is current.

## 6. Troubleshooting

| Symptom                                       | Likely cause and fix                                                                                                                                |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WASM for <crate> not found at ...`           | The Rust build was skipped. Install the Rust toolchain and the `wasm32v1-none` target, then run `pnpm build:contracts`.                             |
| `<crate>: unknown type <Name>`                | A type is referenced but not defined in the same contract spec. Check that the type is `#[contracttype]` and is reachable from a function or event. |
| `Unsupported spec type ...`                   | See section 5.2.                                                                                                                                    |
| `codegen:check` reports `unexpected: ...`     | A file exists in `generated/contracts/` that the generator does not produce. Delete it, or regenerate.                                              |
| Encoders throw `RangeError: u32 out of range` | Expected behaviour. The encoder rejects values outside the Soroban type's range.                                                                    |
